### Iter 0 —— 关键词基线首跑（暴露否定词 bug）

- **变更**：初版 `KEYWORD_RULES`（18 维度关键词词典）。
- **结果**：画像准确率 **35/38 = 0.9211**。
- **错误案例**：

  | 样本 | 维度 | 期望 | 实际 | 原因 |
  | --- | --- | --- | --- | --- |
  | s03 | current_emotion | 悲伤 | 开心 | 「最近总是**不开心**」被 `开心` 命中 |
  | s03 | emotion_tone | 消极 | 积极 | 同上 |
  | s02 | social_circle | 较孤单 | 未知 | 「连说话的人都没有」无对应词 |

- **分析**：正向情感词被**否定结构**误触发，是情感识别最典型的假阳性来源；
  且否定词在关键词**左侧**（`不开心`）。此外口语化表达（"连说话的人都没有"）
  不在词典内。

### Iter 1 —— 单字否定表（修复 s03，但引入新误伤）

- **变更**：引入否定字表 `不没别无未莫`，命中关键词时检查其左侧字符；
  为 `悲伤` 补充"不开心/不高兴/难受"，为 `social_circle` 补充"一个人/没有朋友"。
- **结果**：画像准确率 **35/38 = 0.9211**（总数不变，错误换了一批）。
- **错误案例**：

  | 样本 | 维度 | 期望 | 实际 | 原因 |
  | --- | --- | --- | --- | --- |
  | s05 | attachment_need | 高 | 未知 | 「特**别**想要人陪」中 `别` 被当成否定 |
  | s10 | current_emotion | 开心 | 未知 | 「特**别**开心」同样被误否定 |
  | s10 | emotion_tone | 积极 | 未知 | 同上 |

- **分析**：`别` 是**多义字**——"特别/分别/个别/差别"中是构词成分，不是否定。
  单字否定表过于粗暴，导致"过纠"。

### Iter 2 —— 否定结构正则化（当前版本）

- **变更**：
  1. 否定识别由「单字表」改为**正则**：`否定词 + 可选程度副词`
     （`不/没/无/未` + `太|很|怎么|那么|这么|是|会|能|多|再|有|要|想|什么`）；
  2. `别` 仅当**不处于** `特别/分别/个别/差别/级别/识别/告别/离别/派别/区别/类别`
     等复合词中才视为否定（负向后顾断言）；
  3. 新增**后置否定**识别：`X 都没有 / 没了 / 不存在`（如"我一点压力都没有"）；
  4. 扩充标注样本 10 → 15 条（新增否定、多情绪混合、家庭话题等难例），
     标签数 38 → 50。
- **结果**：

  | 画像抽取准确率 | **50/50 = 1.0000** |
  | 否定结构鲁棒性 | **7/7** |
  | 自测用例通过率 | **28/28 = 100%** |

- **否定专项回归用例**（已固化进 `tests/test_profile.py`，防回归）：

### Iter 6 —— 长对话记忆暴露压缩设计缺陷（重要修复）

- **背景**：任务2 要求"实现 AI 长对话记忆功能，解决聊天失忆"。
  但此前只验证了 **2 轮**召回，证据不足以支撑"长对话"这一说法。
  于是新增 `tests/test_long_memory.py`：前 3 轮植入用户事实，中间 24 轮日常闲聊，
  最后追问早期事实，并**故意调小容量以强制触发压缩**。
- **发现的缺陷**：首跑结果为 **2/3 通过**——"职业"召回**失败**。

  | 追问 | 期望召回 | 首跑结果 |
  | --- | --- | --- |
  | 你还记得我养的猫叫什么吗？ | 豆豆/橘猫 | ✅ 命中 |
  | 我是做什么工作的来着？ | 前端 | ❌ **未命中** |
  | 我最喜欢哪个歌手的歌？ | 周杰伦 | ✅ 命中 |

- **根因分析**：原压缩策略把一批对话里的所有事实**拼接成一大段摘要**
  （"近期聊到：…；…；…"）。文档一长，向量被大量 n-gram 稀释，
  与**短查询**的余弦相似度被拉低到阈值 0.15 以下，于是"检索不到"。
  **即：压缩策略本身在削弱"记忆"能力**，与任务目标背道而驰。
- **修复：改为分层压缩**（`memory_store.py`）

  | 层级 | 内容 | 触发条件 | 设计要点 |
  | --- | --- | --- | --- |
  | L1 | 原始对话轮 `turn` | 最近 N 轮 | 保留完整上下文 |
  | L2 | 事实记忆 `fact` | 原始轮超 `max_dialogue_turns` | **丢弃助手回声**，把用户陈述**逐条**转成独立记忆——每条短而聚焦，向量不稀释 |
  | L3 | 摘要记忆 `summary` | 事实条数超 `max_facts` | 仅此时才合并，牺牲最老记忆的检索粒度换容量 |

  另外：把压缩内部写入改为 `_append()`（不触发容量检查），避免压缩过程递归。

- **修复后结果**：**3/3 全部命中**，且记忆库规模受控。

  ```
  [PASS] 长对话已触发分层压缩(原始轮→事实记忆) | 原始轮=6(<=上限8), 事实=24, 总计=30
  [PASS] 长对话后召回早期事实(猫名) | 命中=True
  [PASS] 长对话后召回早期事实(职业) | 命中=True, top1=我是做前端开发的
  [PASS] 长对话后召回早期事实(歌手) | 命中=True,  top1=我最喜欢周杰伦的歌
  ```

- **同时修正一处错误断言**：原用例断言"必须产生摘要记忆"，但分层后事实数未超
  `max_facts` 时不应产生摘要——断言与设计不符。已改为分别覆盖 L2、L3 两层。
- **结果**：新增「长对话记忆」套件（5 用例），总计 **40/40 = 100%**，全套耗时约 5.9s。

- **经验教训**：**压缩策略与检索质量是一对矛盾**。凡是"把多条信息合并成一条"的
  记忆压缩，都要用"压缩后还能否召回"来验收，而不是只看容量是否下降。
  这也是本模块后续换 ST 嵌入后必须复测的关键项。

### Iter 7 —— 自测工具可诊断性修复（0/6 事件）

- **现象**：使用方反馈自测结果为 **0/6、通过率 0%**（6 个套件全部失败）。
- **排查**：在当前环境用**同一个解释器**（`D:\Python314\python.exe`，Python 3.14.7）
  复跑，结果为 **40/40 = 100%**，**无法复现**。工作区内也不存在会干扰配置加载的
  `config.yaml`（已确认）。推测为**运行期间文件正被改写**或**使用了不同的解释器**。
- **暴露的真实缺陷（本项目自身问题）**：`run_self_test.py` 捕获套件异常时，
  只把 `traceback.format_exc()` 的**最后一行**写进结果，等于**把病因隐藏了**——
  使用方看到 0/6 却拿不到任何可定位的信息。这是工具设计缺陷，必须修。
- **修复内容**：

  | 改进 | 说明 |
  | --- | --- |
  | 错误信息可定位 | 由"最后一行"改为 `异常类型 @ 文件:行号: 消息` |
  | `--debug` 开关 | 失败时打印**完整堆栈** |
  | 报告含堆栈 | `logs/self_test_report.md` 中失败套件附可折叠的完整堆栈 |
  | **环境体检（预检）** | 运行前检查 Python 版本与 numpy；不合格直接明确报错并返回退出码 `3`，不再产生"6 个莫名异常" |
  | 打印解释器 | 报告首部与报告文件均记录 `sys.executable`，便于确认用的是哪个 Python |

- **验证**：错误格式已生效（`ZeroDivisionError @ <string>:2: division by zero`），
  预检正常返回空，全量仍 **40/40**。
- **经验教训**：**测试工具的报错质量，决定了问题能不能被解决。**
  只保留堆栈最后一行，等于把排查成本转嫁给使用者；异常必须带着
  "类型 + 位置 + 消息"出来，并提供 `--debug` 全量堆栈入口。

### Iter 8 —— 画像维度清单竟是「非法 YAML」（重要修复）

- **起因**：Iter 7 预检定位出使用方的 `python` 指向虚拟环境 `D:\py\.venv`（无 numpy），
  安装依赖后恢复 40/40。顺带加固：新增「PyYAML 与内置解析器结果必须一致」用例——
  因为装了 PyYAML 走 PyYAML、没装走内置解析器，两者若不一致，同一份配置在不同机器
  上行为就会不同。
- **立刻抓到一个真 bug**：该用例首跑即 **ParserError**。

  ```
  [FAIL] 套件执行异常 | ParserError @ parser.py:438: while parsing a block mapping
  ```

- **根因**：`profiles/profile_dimensions.yaml` 中 **18 条 `example:` 全部写法非法**：

  ```yaml
  example: "我作为一个男生，压力真的好大" -> 男     # ✗ 标准 YAML 非法
  ```

  标准 YAML 中，**以引号开头的标量，引号结束后不得再跟任何内容**。
  正确写法是整体作为单引号标量：

  ```yaml
  example: '我作为一个男生，压力真的好大 -> 男'     # ✓
  ```

- **影响面（为什么严重）**：内置 `yaml_light` 过于宽容，把它静默当普通字符串收下，
  所以在我这里从未暴露；但**成员3 做画像评测时必然用 PyYAML 读这个文件，
  会直接 ParserError 崩溃**——等于把 bug 潜伏到别人环境、在评测环节才爆。

### Iter 10 —— 防瞎编从「只有提示词」变成「可检测 + 可拦截」

- **背景（先是自我纠错）**：核查代码时发现，此前"减少瞎编"**只靠提示词**——
  属于**软约束**，程序完全无法检测、无法度量、无法拦截。
  而我在 README 里写的"抗幻觉**三重**保障"是**夸大了**：第三重"后处理清洗"
  实际只剥离 `<|im_end|>` 与角色前缀，**并不能识别编造内容**。
  已先更正表述，再补真正的机制。

- **第一版设计（句级，2-gram 重合率）——被实测推翻**：

  | 阶段 | 用例集 | 结果 |
  | --- | --- | --- |
  | a | 7 条近义回声 + 5 条编造 | 阈值 0.25~0.50 **表现完全相同**：0 误判、1 漏报 → 说明用例无区分度，阈值等于拍脑袋 |
  | b | 加 3 条部分重合难例 | 阈值开始有区分：0.30 漏 2 条、0.34 漏 1 条、0.50 漏 0 条 |
  | c | **加 6 条"合法转述"**（真实模型不会逐字复述） | **阈值 ≥0.20 就开始误判合法转述** |

  阶段 c 的误判实例（全部是正常回复，却被判为编造）：

  ```
  用户说"我妈又催婚了"          -> 回复"你妈妈在催婚"        重合率不足
  用户说"我和对象异地"          -> 回复"你和另一半异地"      同义词，重合率不足
  用户说"我养了一只叫豆豆的橘猫" -> 回复"你养的那只猫叫豆豆"   语序变化，重合率不足
  ```

  **结论：句级 2-gram 重合率对同义词与语序太脆弱，不能作为拦截依据。**

- **第二版设计（按精度分级）——采用**：

  | 层级 | 信号 | 精度实测 | 处理方式 |
  | --- | --- | --- | --- |
  | **实体级** | "你的猫""你养的狗""你老婆""你妈""你对象"——断言用户**拥有**某关系/宠物 | 16 条正常回复 **0 误杀**；编造关系 **5/5 拦下** | **拦截**（替换为澄清式回复） |
  | 句级 | "你之前说……""我记得你……" | 会误判合法转述 | **仅记录**，不拦截 |

  关键修复（均为实测驱动）：
  1. `的` 设为**可选** —— 中文亲属称谓常省略（"你老婆""你妈"），原本漏报；
  2. 补**口语缩写**（妈/爸/哥/姐…），长词排前避免"妈妈"被"妈"截断；
  3. 加**变体映射** —— 用户说"我妈"，回复"你妈妈"不应判为编造；
  4. **刻意排除**"工作/公司/学校/同事/朋友"—— 可由上下文合理推断，
     否则"你的工作压力大吗"这类正常回复会被误判；
  5. 泛化建议（"养宠物或许能缓解孤独，你有考虑过吗"）不拦截 —— 已实测确认。

- **最终实测结果**：

  ```
  【拦截层·实体级】误杀正常回复 0/16    抓到编造 5/9（覆盖全部编造关系/宠物类）
  【记录层·句级】  正常回复记为可疑 3/16（不拦截，可接受）
                   编造但仅记录未拦截 2/9  ← 已知局限，如实记录
  ```

- **落地**：新增 `src/anti_hallucination.py`；接入 `DialogueGenerator`
  （支撑上下文 = 本轮输入 + 召回记忆 + 画像 + 最近历史）；每轮结果新增
  `hallucination_check` 字段（可观测命中了哪些断言、是否被拦截）；
  配置项 `persona.hallucination_check`（mode / enforce_entities / report_sentences / 阈值）。
- **新增用例**：「防瞎编校验」套件 7 个用例（含**端到端拦截**与**端到端不误杀**），
  总计 **50/50 = 100%**。

- **经验教训**：**拦截动作必须只绑定高精度信号**。
  误杀一条正常回复的代价（用户觉得"这AI好蠢/答非所问"）远大于漏掉一条编造。
  因此"检测到的全部问题"与"敢据此拦截的问题"必须是两个集合——
  本模块用 `blocking()` 明确区分二者。此外，**评测用例必须包含"合法转述"**，
  否则极易得到"阈值怎么调都一样"的假结论。

### Iter 11 —— RAG 检索质量系统性调优（本轮价值最高）

- **起因**：继续闭环剩余缺口——② 阈值标定脚本缺失、⑥ 标注样本偏小。
  新建 `calibrate_threshold.py` + `data/memory_eval.json`，把标定从"拍脑袋"变成"可测量"。

- **发现 1：评测集规模直接决定结论可靠性**

  | 标注集 | 扫描结论 |
  | --- | --- |
  | 12 条查询 | 最优 n-gram = **1-3**（当时默认） |
  | **扩到 30 条查询** | 最优 n-gram = **1-2**，且 1-3 明显更差 |

  **同一份代码，两个相反结论**——说明 12 条时纯属噪声。教训：**结论的置信度取决于评测集规模**，
  小样本上的"A 优于 B"不可信。这也是把缺口⑥（样本偏小）一并修掉的价值。

- **发现 2：绝对阈值这个机制本身就不对**

  实测**同一条目标记忆**在不同提问措辞下的相似度：

  | 查询 | 目标记忆得分 |
  | --- | --- |
  | `猫` | 0.218 |
  | `你还记得我养的猫叫什么吗？` | 0.175 |
  | `猫怎么样` | **0.082** |
  | `我养的那只猫最近怎么样` | 0.238 |

  **相差 3 倍，但排序始终正确**（猫永远排第一）。在一个会随措辞漂移的量上画固定绝对线，
  必然时松时紧。→ 改为**相对下限过滤**：`floor = max(绝对下限, top_score × relative_ratio)`。
  实测（30 条）：绝对模式最优 F1 0.667 → 相对模式 0.676。

- **发现 3（本轮最关键）：虚词噪声导致排序错误**

  长对话测试中，查询"你还记得我养的猫叫什么吗？"**检索不到猫的记忆**，前 3 名全是无关的
  日常闲聊回声。实测分数：

  ```
  0.311  无关的日常回声（"小暖：我在听…你说到今天没什么特别的…"）
  0.175  真正相关的"我养了一只叫豆豆的橘猫"     ← 排序错误！
  ```

  **根因**：查询含大量虚词单字（你/我/的/什/么/吗 共 6 个），而这些虚词在任意中文句子里
  都高频共现，产生了虚假相似度。**加大向量维度治不了**（已实测 dim 256→4096，
  回声得分仅从 0.363 降到 0.231，排序依旧错）。

  **修复**：按信息量给 n-gram 加权——**只由虚词构成的 n-gram 降权至 0.15**。实测：

  | 虚词权重 | 猫 | 无关回声 | 排序 |
  | --- | --- | --- | --- |
  | 1.0（不降权） | 0.175 | **0.311** | ✗ |
  | **0.15** | **0.221** | 0.115 | ✓ |

  排序反超且区分度健康（1.9 倍）。

- **修复后重新标定（30 条查询）**：

  | 模式 | Recall | Precision | F1 |
  | --- | --- | --- | --- |
  | 绝对阈值最优 | 0.633 | 0.950 | 0.760 |
  | **相对下限最优**（ratio=0.8, 绝对下限=0.10） | **0.800** | **0.857** | **0.828** |

- **净提升（全部零依赖，未安装任何新库）**：

  | 指标 | 改动前 | 改动后 |
  | --- | --- | --- |
  | Recall@5 | 0.667 | **0.800** |
  | Precision@5 | 0.667 | **0.857** |
  | F1 | 0.667 | **0.828** |

- **同时修正一处我自己的判断错误**：标定脚本最初在 F1 并列时取"更保守（更高阈值）"，
  但那会**牺牲召回**——而本模块的目标恰是"**解决聊天失忆**"，漏召回（忘事）的代价
  大于多召回（提示词里多一条无关记忆）。已改为默认偏好召回，并提供 `--prefer precision`。

- **其他落地**：
  - 新增回归用例「虚词降权：自然句查询排序正确」，防止该修复被无意回退；
  - 补齐**持久化测试**（5 个用例）——此前 `memory.save/load`、`save_profiles/load_profiles`、
    `pipeline.save/load` **零覆盖**；实测**未发现 bug**（代码本就正确），但现在有了保障；
  - 结果：**56/56 = 100%**（8 个套件）。

- **经验教训**：
  1. **评测集规模决定结论可信度**——12 条与 30 条给出相反答案，小样本结论必须存疑；
  2. **不要在会漂移的指标上画固定阈值**，改用相对/排序口径更稳；
  3. **中文短文本检索的首要噪声是虚词**，按信息量加权是零成本高收益的手段；
  4. 即便如此，零依赖方案 Recall 0.800 已接近上限，**换 ST 嵌入仍是下一个杠杆**。

### Iter 14 —— 推送工具（并修掉一个环境坑）

- **背景**：Iter 13 建好本地仓库后，远程推送需要授权。使用方选择"自己建空仓库、
  由我们负责推送"，故需要一个可复用的推送脚本，便于后续每次改动都能推上去。
- **遇到的环境坑**：先写了 `push_to_github.ps1`，实测直接失败——

  ```
  SecurityError: 无法加载文件 push_to_github.ps1，因为在此系统上禁止运行脚本。
  ```

  Windows 默认 **PowerShell 执行策略禁止运行 `.ps1`**。这会让使用方同样撞墙。
  → **改用 Python 实现** `push_to_github.py`：本项目本来就需要 Python，
  且 Python 不受执行策略限制，跨平台（Linux/macOS）也能用。

### Iter 16 —— 适配团队真实仓库（llb016/digital_human）

- **背景**：发现团队真实项目仓库 `llb016/digital_human`，其技术约定与本模块
  存在 **6 处不一致**，若不处理，本模块接进去会**静默退回 mock**（读不到团队配置）。

  | 项 | 团队约定 | 本模块原状 |
  | --- | --- | --- |
  | 大模型调用 | `model_path: "./model/qwen2.5"` **本地 transformers 加载** | OpenAI 兼容 HTTP API |
  | 配置结构 | **扁平** key | 嵌套分节 |
  | 模块位置 | `modules/memory/` | 仓库根下的独立目录 |

  团队实际下载的权重是 **Qwen2.5-1.5B-Instruct**（modelscope，bf16，约 2.9GB），
  经确认：**没有起 HTTP 服务**，就是在代码里用 transformers 加载。

- **改动 1：新增 `transformers_local` 后端**（`src/llm_client.py`）
  - 进程内加载：`AutoModelForCausalLM` + `torch_dtype="auto"`（bf16 权重不放大成 fp32）
    + `device_map="auto"`（有 GPU 用 GPU，无则 CPU）；
  - 用 `tokenizer.apply_chat_template` 生成输入，**保证与 Qwen 的 ChatML 格式一致**
    （手拼 `<|im_start|>` 极易出错）；
  - **懒加载 + 复用**：权重只加载一次；另提供 `warmup()`，供主程序启动时预加载，
    把加载耗时移出"首次请求延迟"（直接影响「推理性能」评分）；
  - 只解码新生成 token（切掉输入 prompt），并 `skip_special_tokens=True`。

- **改动 2：配置适配层**（`src/config_loader.py`）
  - 扁平 → 嵌套映射：`model_path` / `max_new_tokens` / `temperature` /
    `embedding_model` / `vector_db_path`；
  - **存在 `model_path` 时自动把 backend 切为 `transformers_local`** ——
    否则会拿着一个权重目录去请求 HTTP 接口，连不上还看不出原因；
  - 提供 `backend_explicit: true` 逃逸口（强制 mock 做离线自测）。

- **改动 3：配置查找改为向上逐级**（`find_public_config`）
  - 原来写死 `../config.yaml`；模块放进 `modules/memory/` 后该路径变成
    `modules/config.yaml`（不存在）→ **静默退回默认值**；
  - 改为向上一级级查找（最多 3 层），两种布局都能命中。

- **改动 4：修掉一个潜伏已久的严重 bug（本轮最大收获）**
  - `_deep_merge` 顶层用 `dict(base)`（**浅拷贝**），导致 `cfg["model"]`
    与 `DEFAULTS["model"]` **是同一个对象**；任何原地修改都会
    **永久污染全局默认值**，使后续每次 `load_config` 都串到上一次的值。
  - 触发场景：适配器往 `cfg["model"]` 写 `model_path` 后，**所有后续加载都被污染**——
    测试中表现为"空环境下也读出了 transformers_local"。
  - 影响面：生产同样致命——同一进程内创建两个 `CompanionPipeline` 实例，
    第二个会拿到第一个的配置；配置热重载也会串值。
  - 修复：`_deep_merge` 全程 `copy.deepcopy`。
  - **该缺陷由"多环境隔离"用例暴露**——若只测"单次加载"，它会一直潜伏。

- **改动 5：错误提示改为一次列出全部缺失项**
  - 原先依赖检查与目录检查串行，只报第一个；改为汇总后一起报
    （缺目录 + 缺依赖时报"发现 2 个问题"），避免"修一个又撞一个"。

- **新增用例**：「团队仓库适配」套件 **9 个**（扁平映射、双布局查找、默认回退、
  explicit 逃逸、误判防护、两条后端失败路径、**多次加载互不污染回归**）。

- **结果**：用例 **70/70 = 100%**（10 个套件）。

- **待实测（重要）**：本机 **torch / transformers 未安装**，本地模型加载路径
  **尚未真机验证**（已验证的是配置适配与失败路径）。需
  `pip install torch transformers accelerate` 后跑 `python check_model.py` 做端到端确认。

- **给团队的三条提醒（只提醒，不改团队仓库）**：
  1. **`logs/` 被 `.gitignore` 忽略** —— 任务书要求日志入库供评审（「平台运行记录」10 分），
     当前所有日志都在仓库外，**评审看不到运行记录**；

- **经验教训**：

### Iter 18 —— 真实 Qwen 端到端跑通，并解决一个 2.8 倍性能问题

- **环境安装**（本机无 NVIDIA GPU，Intel Arc 核显 → CPU 推理）：
  `torch 2.14.1+cpu` / `transformers 5.19.0` / `accelerate 1.15.0`
- **首次端到端跑通**：`check_model.py` 在团队布局下成功加载 Qwen2.5-1.5B 并生成中文共情回复。
  权重加载 12~13s；输出无 ChatML 标记泄漏。

- **发现 1：团队 `model_path` 与实际权重位置不匹配**
  团队配置写 `./model/qwen2.5`（相对仓库根，`.gitignore` 也忽略了 `model/`），
  但权重实际下载到了仓库**外面**（`D:\动感地带1\model\qwen2.5`）。
  - 处理：用**目录联接（junction）** `digital_human\model -> ..\model`，
    瞬时完成、不复制 2.9GB、不产生额外占用；
  - 同时改代码：`model_path` 由"相对进程 CWD"改为**相对 config.yaml 所在目录**解析，
    消除对启动目录的依赖（原先只有恰好在该目录启动才找得到权重）。

- **发现 2（本轮最大收获）：CPU 上 bf16 比 fp32 慢 2.8 倍**
  `torch_dtype="auto"` 会按权重加载成 bf16。而本机 CPU（Intel Core Ultra 7 155H）
  **没有 AVX512-BF16**，bf16 矩阵乘走软件模拟：

  | 精度 | 同一 prompt / 同一输出 | 速度 |
  | --- | --- | --- |
  | bf16（auto 的结果） | 22.5 s | 1.29 tok/s |
  | **fp32** | **8.0 s** | **3.63 tok/s** |

  - 修复：`_dtype_kwargs()` 按设备选精度——**CPU（含 `device: auto` 且无 CUDA）用
    float32**，有 GPU 才交给 transformers 自适应；
  - 第一次修复漏判：只写了 `device == "cpu"`，而配置默认是 `"auto"`，
    于是又退回 bf16、延迟无改善（31/33/42s）。改为判断
    `device == "cpu" or (device == "auto" and not torch.cuda.is_available())` 后生效；
  - 真实多轮链路实测（修复前 → 后）：

    | 轮次 | bf16 | fp32 |
    | --- | --- | --- |
    | 直接调用 | 5.08 s | **2.16 s** |
    | 第1轮 | 31.44 s | **14.63 s** |
    | 第2轮 | 33.22 s | **9.41 s** |
    | 第3轮 | 41.93 s | **10.40 s** |

  - 顺带修掉 `torch_dtype` 废弃告警：transformers 5.x 已改名为 `dtype`，
    按主版本号选择关键字，兼容 4.x。

- **发现 3：int8 动态量化在本场景不可用**
  `torch.quantization.quantize_dynamic` 后推理报
  `RuntimeError: qlinear_dynamic (ONEDNN): data type of input should be float`
  —— oneDNN 的量化线性层要求 fp32 输入，而模型是 bf16。
  若要走量化路线，需先用 fp32 加载再量化（显存/内存翻倍），后续可评估。

- **性能剖析（供后续优化）**：
  - 生成速度约 3.6 tok/s（fp32），**但主要成本在预填充**：
    实测约 16 tok/s 的预填充速度，而本模块的 system prompt 达 **281 tokens**
    （440 字，其中"护栏"部分占 231 字，接近一半）；
  - 因此下一步优化优先级：**① 精简 system prompt（护栏压缩）→ ② 减少
    `max_new_tokens`（团队配置为 200，对话场景 60~80 足够）→ ③ 静态前缀 KV 复用**。

- **模型能力观察（1.5B）**：第 3 轮"你还记得我是做什么的吗"的回答**不稳定**——
  bf16 那次答对了（"你是北京的一名IT互联网程序员"），fp32 那次却答
  "哈哈，忘记了吧？"并转移话题。说明 **1.5B 的指令跟随与画像利用能力偏弱**，
  建议评估是否升级到 3B/7B（会牺牲速度，需权衡「推理性能」与「回应质量」两项评分）。

- **结果**：自测仍 **70/70 = 100%**。

- **经验教训**：**"auto" 不一定是"自动最优"**。`torch_dtype="auto"` 只按权重精度选择，
  并不知道目标硬件是否支持该精度；在 CPU 上它会稳定地选到最慢的那一个。
  凡涉及硬件相关的默认值，都应**实测后按设备显式选择**，而非信任 auto。

### Iter 19 —— 新增交互式对话入口（人工输入文本测试）

    与本模块规则抽取的 `current_emotion`（进【用户画像】），二者可能矛盾。
  - 处理：**从画像维度中移除 `current_emotion`**（维度 18 → 17），
    同时删除 `KEYWORD_RULES` 中对应规则、并清理标注样本里 10 处相关期望（标签 50 → 40）。
  - 保留 `emotion_tone`（整体情绪基调）——它是**跨轮次的长期画像属性**，
    与成员1 的**逐轮瞬时情绪**粒度不同，不冲突，且已在维度文档中写明区别。

- **改动 2：`emotion.labels` 从"死配置"变成"观测探针"**
  - 核实发现：该配置**此前从未被任何代码读取**（只在测试里被引用），属于配了没用的死配置。
  - 改为：声明成员1 的标签集；实际收到的标签若不在其中，记入 `unseen_emotions`
    并通过 `emotion_report()` 输出，**但绝不拦截、不拒绝**（逐轮情绪一律以成员1 为准）。
  - 这样配置有了真实用途：**发现两侧标签口径漂移**，而不是静默接受。

- **改动 3：配置格式统一为团队扁平格式**
  - `config.example.yaml` 整体重写为**纯扁平**，与团队 `config.yaml` 完全同构，
    不再让团队面对本模块的嵌套结构（嵌套仅是内部实现细节）。
  - `TEAM_FLAT_KEY_MAP` 从 5 个键扩展到 21 个：团队原有 5 键原样保留，
    本模块可调项（`similarity_threshold` / `relative_ratio` / `memory_top_k` /
    `default_persona` / `embedding_backend` / `dtype` 等）**一律用扁平键**暴露。
  - **踩到一个键名冲突**：最初用 `persona` 作扁平键，而它与内部节名同名，
    扁平值会在合并阶段把整个 `persona` 分节覆盖成字符串，报出晦涩的
    `TypeError: 'str' object does not support item assignment`。
    已改为 `default_persona`，并新增**冲突检测**：任何遮蔽分节名的顶层键都会
    直接报出可操作的错误提示（不再让人面对 TypeError）。
  - 模板里 `model_path` 默认注释：置空即退回 mock，使无权重机器也能跑自测。

- **改动 4：提示词精简（性能）**
  - 护栏由 5 条 231 字压到 3 条约 110 字，**禁编造/禁臆测/专业边界/危机转介/简短回复
    五项一条不落**；沟通原则与护栏改为单行连接，去掉冗余编号与结尾指令。
  - system prompt：**440 字 / 281 tokens → 338 字 / 223 tokens（省 21%）**。
  - 真实 Qwen 实测延迟：**14.6/9.4/10.4s → 13.7/8.3/8.1s**。
  - 新增回归用例「提示词长度受控(<=420字)」，防止后续又膨胀回去。

- **结果**：用例 **75/75 = 100%**（10 个套件）。

- **模型升级建议（负责人已确认 1.5B 不够）**：实测第 3 轮"你还记得我是做什么的吗"
  **多次答错**（"我好像忘记我们上次聊了些什么"），说明 1.5B 无法稳定利用注入的画像。
  建议升到 **Qwen2.5-3B-Instruct**：本机 CPU（22 线程）下 1.5B 约 8~14s/轮，
  3B 预计 20~30s/轮，7B 会到 60s+ 不适合交互。**这是「回应质量 20 分」与
  「推理性能 10 分」之间的直接权衡**，建议先升 3B 实测再定。
  下载命令：`python -c "from modelscope import snapshot_download; snapshot_download('Qwen/Qwen2.5-3B-Instruct', local_dir='./model/qwen2.5')"`

- **经验教训**：
  1. **"配了但没用"的配置比没有配置更危险** —— 它会让协作者以为已经对接好了；
     凡新增配置项，必须同时问一句"谁在读它、读不到会怎样"。
  2. **扁平键与内部分节同名会静默毁掉整个分节**；跨格式适配必须显式做键名冲突检测。

### Iter 21 —— 撤回"1.5B 不够"的结论：根因在我的提示词

- **决策**：负责人决定**继续使用 Qwen2.5-1.5B**，不升级 3B。
  已中止 3B 下载并清理残留（2.58 GB），确认 1.5B 权重完好（2.88 GB）。

- **自我纠错（本轮最重要）**：我此前在 Iter 18 判断"1.5B 指令跟随偏弱、
  多次答错『你还记得我是做什么的吗』"，并据此建议升级模型。
  **这个判断是错的**——根因在**我自己的提示词**：

  | 环节 | 原文 | 问题 |
  | --- | --- | --- |
  | 护栏第 1 条 | "只依据【用户画像】【相关记忆】了解用户；**记忆为空就直说不了解**" | 把"**没有召回记忆**"等同于"**没有信息**"。而当时画像里明明有"职业=IT互联网"，模型却严格照做指令回答"我好像忘记我们上次聊了些什么" |
  | prompt 结构 | 画像/记忆/情绪排在**护栏之前** | 小模型长上下文注意力弱，关键信息离提问越远越容易被忽略 |

  换句话说：**是我写了一条会诱导模型"装失忆"的指令，然后怪模型不行。**

- **修复 1：护栏语义修正**
  - 改为："回答涉及用户个人信息（职业、兴趣、经历等）的问题时，**先查【用户画像】与【相关记忆】，有就据实回答**；两者都没有相关信息时才说不了解。禁止编造用户过往。"

- **修复 2：调整 prompt 结构（近因效应）**
  - 顺序由「人设 → 画像/记忆/情绪 → 护栏」改为
    「人设 → 护栏 → **画像/记忆/情绪**」，让最相关的上下文**紧邻用户提问**。

- **实测对比（真实 1.5B，同一场景，temperature=0.7）**：

  | 版本 | 成功率 | 典型回答 |
  | --- | --- | --- |
  | 修复前 | 2/3 | "对不起，我好像忘记我们上次聊了些什么" |
  | 仅修护栏 | 2/3（仍不稳） | 一次答对（"我记得你是做程序员的小伙子"），一次答"我并没有记录到过你的信息" |
  | **护栏 + 顺序** | **3/3** | "是的，我记得你是做新媒体运营的"／"我了解了，你是做新媒体运营的"／"我记得你是一个……新媒体运营人员" |

- **副产品：抓到一处画像抽取误报**
  第 3 次复测模型答"在**IT互联网行业**工作的新媒体运营人员"——模型没错，是**我的词典错了**：
  `IT互联网` 的关键词里含裸"运营"，而"新媒体运营/电商运营"并非 IT 岗。
  - 已从关键词中移除裸"运营"，并加入误报回归用例（4/4 通过）。

- **结果**：用例 **75/75 = 100%**；提示词 364 字（仍在 420 字上限内）。

- **经验教训**：
  1. **不要轻易把问题归因于"模型能力不足"**。这次差一点因为误判去升级模型
     （多下 6GB 权重、每轮慢 2~3 倍），而真正要改的是我写错的一条护栏。
     **在换模型之前，先把提示词读到能逐字解释"模型为什么这样答"。**
  2. **小模型对信息位置敏感**：同样的内容，放在末尾（紧邻提问）比放在中间有效。
  3. **模型答错时，先分辨是"模型错"还是"喂给它的数据错"**——
     本例中模型忠实复述了画像里的错误值，错在抽取端。

### Iter 22 —— 再次更正归因：延迟主导因素是「生成长度」，不是预填充

- **又一处自我纠错**：Iter 20 我曾判断"**CPU 预填充是主要成本**"，并据此认为
  提示词精简是性能主杠杆。**这个判断是错的**——实测拆解：

  | 项 | 实测 |
  | --- | --- |
  | 预填充（prompt 268 tokens） | **仅约 2 秒** |
  | 生成速度 | 4.3 ~ 5.5 tok/s |
  | 一次 99 token 的回复 | **21.9 秒** |

  我此前把"总耗时"直接除以 token 数，**把预填充时间算进了生成速度**，
  于是得出"预填充慢"的错误结论。→ 更正：**生成长度才是延迟主导因素**。

- **尝试 1：把上限降到 80（负责人指示）——实测不成立**
  - 只在"长回复"那一例生效（99 → 80 token），总时长 39.9s → 36.8s（约 8%）；
  - **但把回复截断在半句话上**（⚠️），体验反而变差。
  - 结论：**硬截断不是正确手段**。

- **尝试 2：上限设 120 做安全网 + 提示词里写明确字数——成立**
  - 护栏第 3 条由"回复简短自然（1~3 句）"改为
    **"回复控制在 2~3 句、60 字以内"**（给小模型可度量的目标）；
  - 实测（同一组 3 例，未采样）：

    | 用例 | 原来（上限 200） | 现在（字数约束 + 上限 120） |
    | --- | --- | --- |
    | 一般倾诉 | 63 tok / 14.5 s | **23 tok / 6.6 s** |
    | 简单提问 | 22 tok / 4.8 s | 15 tok / 4.8 s |
    | 复杂提问 | 99 tok / 21.9 s | **62 tok / 11.5 s** |
    | **合计** | **39.9 s** | **22.9 s（省 43%）** |

  - **零截断**（全部以句号/问号正常结束）；另一组复测**平均 9.6 s/轮**。

- **落地**：新增扁平键 `max_reply_tokens`（默认 120），
  实际生效值 = `min(本值, 团队 config.yaml 的 max_new_tokens)`——
  **不越权修改团队配置**，只在调用处收紧本模块的回复长度策略。

- **结果**：用例 **75/75 = 100%**；提示词 374 字（仍在上限内）。

- **经验教训**：
  1. **我第二次犯了"凭直觉归因"的错**（先是怪模型不行，再是怪预填充慢）。
     两次都是**测量之后才发现归因错了**。凡性能结论，必须给出可拆解的分解
     （预填充 vs 生成分开计时），不能只看总耗时。
  2. **约束模型行为要靠"说清楚要什么"，而不是"事后砍掉"**。
     把上限从 200 砍到 80，模型照样想写长，只是被截断在半句话；
     而明确告诉它"60 字以内"，它会主动写短。**后者既省时间又不损质量。**

### Iter 23 —— 澄清与成员1 的依赖关系，并固化为接口契约

- **起因**：使用方质疑"成员1 的内容不是和我的部分有关系吗"。
  我此前说"**成员1 后续提交完全不受影响**"，**这个说法不准确**——
  它只覆盖了文件层，掩盖了功能层的依赖。

- **实测澄清（三种场景）**：

  | 场景 | 提示词中的情绪段 | 是否正常对话 |
  | --- | --- | --- |
  | 成员1 未就绪（不传 `emotion_label`） | `【当前情绪】（未知）` | ✅ 正常 |
  | 成员1 就绪（传已知标签） | `【当前情绪】疲惫` | ✅ 正常 |
  | 成员1 用了配置外标签（"烦躁"） | `【当前情绪】烦躁` | ✅ 正常，且记入漂移清单、**不拦截** |

- **准确的关系描述**（分两个维度，此前只说了第一个）：

  | 维度 | 是否受影响 |
  | --- | --- |
  | **代码/文件** | 不受影响——不 import 对方代码、目录零重叠，**不阻塞双方提交** |
  | **功能/数据** | **有依赖**——成员1 产出情绪标签，本模块消费它生成回复，**集成时必须对接口** |

  教训一句话：**"不阻塞你提交" ≠ "不需要对接"**。协作说明必须点明依赖，否则对方会以为可以各做各的。

- **落地 1：新增接口契约文档** `docs/interface_for_member1.md`，包含：
  - 数据流图（成员1 → 主程序 → 本模块）与"不经代码耦合"的说明；
  - `emotion_label` / `user_id` 参数约定与本模块的三条保证（不校验、不反向依赖、结果可观测）；
  - **成员1 需要做的三件事**：声明标签集 / 输出单字符串标签（建议带置信度）/ 与主程序约定调用顺序；
  - 可直接复制的 5 行集成示例；
  - 已知风险表（标签不一致、阈值两边各判一次、双标签冲突、主程序忘传 label）及处理方式；
  - 集成后的快速自检清单。

- **落地 2：新增 3 个接口契约回归用例**（不传标签 / 传已知标签 / 传未知标签），
  把"契约行为"变成机器可校验的，防止后续改动悄悄破坏对接。

- **结果**：用例 **78/78 = 100%**（10 个套件）。

- **经验教训**：**描述协作影响时，必须区分"文件层"与"功能层"，并明确说出依赖方向。**
  一句过于乐观的"不受影响"，可能让对方跳过接口对齐，最终在集成阶段才暴露问题。

### Iter 24 —— 性能优化第二轮：把剩余空间摸清楚

- **背景**：使用方问"还能再优化吗"。逐项做实验，**用数据判死刑或采纳**。

- **实验 1：线程数调优 —— 无空间**

  | 线程数 | 生成速度 |
  | --- | --- |
  | 8 | 2.92 tok/s |
  | **16（当前）** | **2.97 tok/s** |
  | 22（=逻辑核数） | 2.37 tok/s（**更慢**，线程争抢） |

  结论：当前 16 已是最优，**调线程没有收益**。

- **实验 2：int8 动态量化 —— 快但废，否决**

  之前 int8 失败是因为模型以 bf16 加载（oneDNN 要求 fp32 输入）；改 fp32 后可量化，
  等长对比（强制生成 60 token）：

  | 精度 | 速度 | 输出 |
  | --- | --- | --- |
  | fp32 | 2.85 tok/s | "听起来你正在考虑你的未来方向…你可以先列出一些你对新城市的期待和担忧" ✅ |
  | int8 | **5.06 tok/s（快 1.78×）** | "我最近在使用一个名为「小暖」的应用程序，它似乎是一个面向公众的平台…" ❌ |

  **量化后模型开始语无伦次、把自己描述成一个 App。1.5B 参数量太小，扛不住朴素
  int8 动态量化**（无校准、逐张量）。→ **否决**：不能为了速度牺牲质量。

- **实验 3：拆解耗时构成 —— 生成占 74%**

  | 历史长度 | prompt | 预填充 |
  | --- | --- | --- |
  | 0 轮 | 268 tok | 3.56 s |
  | 4 轮 | 468 tok | 5.30 s |
  | **8 轮（当前上限）** | 668 tok | 7.31 s |

  对比"生成 60 token ≈ 21 s"，**预填充只占约 26%，生成占 74%**。
  → 把历史从 8 轮降到 4 轮可省约 **2 s/轮**，但会损失上下文；列为可选项，暂不改默认。

- **实验 4：发现并修复"提示词重复注入"（本轮唯一采纳项）**
  - 现象：连聊几轮后提问，**同一条内容在提示词里出现两次**——
    一次在 `【相关记忆】`（RAG 召回），一次在原始历史消息里。
    实测："我周末喜欢打篮球，每周都去球场" 同时出现在两处。
  - 根因：RAG 记忆库会把**最近几轮**也存进去，而最近几轮**本来就在历史窗口里**。
    RAG 的价值是"想起很久以前的事"，检索最近的原话纯属浪费 token，
    还可能让模型误以为用户强调过。
  - 修复：以历史窗口的正文为排除集，`【相关记忆】`只注入**历史之外**的记忆。
  - 验证（关键）：**长程召回未被误伤**——把关键信息挤出历史窗口后，
    "我养了一只叫豆豆的橘猫" 仍能被 RAG 想起。

- **顺带修正一个"测机制而非测结果"的坏用例**
  原用例断言"必须由 RAG 召回科幻电影"。去重后，最近几轮不再走 RAG，用例失败——
  但**信息仍通过历史消息对模型可见**，功能没坏。
  → 改为断言**结果**（"该信息在本轮上下文中可见"），并补两个用例：
  「记忆去重（不与历史消息重复注入）」与「长程召回（历史窗口外仍能想起）」。

- **结果**：用例 **80/80 = 100%**。

- **优化空间总结（如实）**：

  | 手段 | 效果 | 状态 |
  | --- | --- | --- |
  | CPU 用 fp32（而非 bf16） | **2.8×** | ✅ Iter 18 |
  | 提示词精简 | prompt 281→223 tok | ✅ Iter 20 |
  | 明确字数约束 | 总时长 **-43%** | ✅ Iter 22（收益最大） |
  | 记忆去重 | 去掉重复注入 | ✅ Iter 24 |
  | 生成长度上限降到 80 | 会截断半句话 | ❌ 否决，取 120 |
  | 线程数调优 | 16 已最优 | ❌ 无空间 |
  | int8 量化 | 快 1.78× 但质量崩 | ❌ 否决 |
  | 历史 8→4 轮 | 省 ~2 s/轮 | ⚠️ 可选，有取舍 |

  **结论：在现有硬件（无 GPU、1.5B、transformers 直跑）下，程序已接近优化上限。**
  生成速度 2.9~5.1 tok/s 是硬约束，而它占总耗时 74%。
  真要再快，只有换路径：**OpenVINO / IPEX（Intel CPU 专用推理加速，需换推理后端并重验质量）**
  或换硬件 —— 不属于应用层优化。

- **经验教训**：
  1. **"能优化"必须用数据回答，不能凭感觉**。本轮 5 个候选里只有 1 个可行，
     其余要么无效（线程）要么有害（int8）。
  2. **量化不是免费的**——它在小模型上可能直接毁掉输出质量，
     **必须做等长对比并肉眼检查输出**，只看 tok/s 会得出错误结论。
  3. **测试要测"结果"而不是"实现机制"**，否则重构（如去重）会让正确的改动测出失败。

| 结果格式化注入提示词 | PASS | 输出含文本、类型与相关度 |
| 一轮对话记录 2 条记忆 | PASS | user/assistant 各一条 |
| 持久化 round-trip | PASS | 原 5 条 → 载入 5 条 |
| 分层压缩 L2(原始轮→事实) | PASS | max_turns=5 时原始轮=3、事实=5、摘要=8、总=16 |
| 分层压缩 L3(事实→摘要) | PASS | 事实=5 ≤ 上限 6，摘要=8 |
| 虚词降权：自然句排序正确 | PASS | top1=cat，得分 0.221 |

**检索质量（`data/memory_eval.json`，30 条标注查询，top_k=5）**：

| 指标 | 改动前 | 当前 |
| --- | --- | --- |
| Recall@5 | 0.667 | **0.800** |
| Precision@5 | 0.667 | **0.857** |
| F1 | 0.667 | **0.828** |

复现：`python calibrate_threshold.py`（对比绝对/相对两种过滤并给出推荐配置）

**观察与结论**：
- 检索采用**相对下限 + 绝对下限**双重过滤。原因见 Iter 11：同一目标记忆在不同
  提问措辞下相似度相差 3 倍（0.082~0.238），但排序始终正确——在漂移量上画固定
  绝对线必然时松时紧。绝对下限 0.10 仅用于筛除"完全无关"。
- **虚词降权是本轮最大收益点**：查询中的"你/我/的/什/么/吗"等虚词与任意中文句子
  高频共现，会盖过真正有信息量的词。降权至 0.15 后，无关回声得分由 0.311 降至
  0.115，正确记忆由 0.175 升至 0.221，排序反超。
- 压缩策略：**分层**（原始轮 → 逐条事实 → 摘要）。注意 Iter 6 的教训——
  早期"拼成一大段摘要"的做法会稀释向量、导致短查询检索不到，已修正。
- **零依赖方案已接近上限**：Recall 0.800。换 `sentence-transformers` 是下一个杠杆，
  但**换后端后必须重跑 `calibrate_threshold.py`**（ST 相似度分布与 hashing 差异极大）。
