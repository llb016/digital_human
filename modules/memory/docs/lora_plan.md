# LoRA 微调预案（成员2 · 对话生成）

> 状态：**暂缓执行（方案已就绪）**。
> 决策依据（已与项目负责人确认）：团队当前**暂无可用 GPU 训练资源**，
> 因此本阶段按 **「人设提示词 + RAG 深耕」** 路线推进；LoRA 预案与数据格式先行备好，
> 待后续获得算力、且提示词/RAG 用尽后指标仍不达标时，可立即启动，无需重新设计。
> 提前写好本方案，是为了让"提示词调优"与"权重微调"两条路线可无缝切换。

---

## 一、优先做提示词工程，而非直接微调

微调成本高、迭代慢，且会削弱模型的通用能力。按以下顺序推进：

| 阶段 | 手段 | 成本 | 预期收益 |
| --- | --- | --- | --- |
| P0 | 人设提示词 + 画像/记忆注入（**已完成**） | 低 | 高 |
| P1 | few-shot 示例、思维链、输出格式约束 | 低 | 中 |
| P2 | RAG 检索质量优化（换嵌入模型、调 top_k/阈值） | 中 | 中高 |
| P3 | **LoRA 微调**（本方案） | 高 | 中（风格/共情对齐） |

只有 P0~P2 用尽仍有明显差距时，才进入 P3。

---

## 二、微调目标（只解决提示词解决不了的问题）

1. **共情表达风格对齐**：稳定输出温暖、简短、口语化的陪伴式回复，
   减少"客服腔""说教腔"和机械罗列建议。
2. **抗幻觉**：在不知道用户信息时坦诚说"我不了解"，
   而不是编造用户过往或编造事实。
3. **安全边界**：遇到自伤等高风险话题，稳定给出温和的转介建议。

**不用于**：注入事实知识（那是 RAG 的职责）、提升情感分类准确率（那是成员1 的职责）。

---

## 三、训练数据格式

统一使用 **sharegpt / messages 多轮格式**（LLaMA-Factory、peft 均支持）。
存放于 `data/lora/train.jsonl`，每行一条样本：

```json
{"messages": [
  {"role": "system", "content": "你是温暖倾听者小暖……（与 persona_prompts.py 保持一致）"},
  {"role": "user", "content": "今天被领导骂了，好难受"},
  {"role": "assistant", "content": "被当众批评确实很难受，先别急着怪自己。想说说当时发生了什么吗？"}
]}
```

抗幻觉样本（负样本对齐）：

```json
{"messages": [
  {"role": "system", "content": "你是温暖倾听者小暖……"},
  {"role": "user", "content": "你还记得我上次说我养的猫叫什么吗？"},
  {"role": "assistant", "content": "抱歉，我这边没有你提过养猫的记录，你再和我讲讲好吗？"}
]}
```

### 数据规模建议

| 类型 | 条数 | 说明 |
| --- | --- | --- |
| 共情回复 | 800~2000 | 覆盖焦虑/悲伤/愤怒/孤独/疲惫等情绪 |
| 抗幻觉（拒答/澄清） | 200~400 | 关键，直接对应"减少瞎编" |
| 安全转介 | 100~200 | 自伤/危机话题 |
| 简短闲聊 | 200~400 | 维持自然口语风格 |

> 数据来源：公开中文情感陪伴对话语料 + 自建 + 对统一大模型的高质量回复做蒸馏筛选。
> **注意**：涉及真实用户对话必须脱敏，且需获得授权。

## 四、训练配置（推荐起点）

以 LLaMA-Factory 为例（模型确认后替换 `model_name_or_path`）：

```yaml
model_name_or_path: <团队确定的开源模型，如 Qwen2.5-7B-Instruct>
stage: sft
do_train: true
finetuning_type: lora
lora_rank: 16            # 起点；效果不足可试 32
lora_alpha: 32
lora_dropout: 0.05
lora_target: all         # 或 q_proj,k_proj,v_proj,o_proj
dataset: emotion_companion
cutoff_len: 2048
template: qwen
learning_rate: 1.0e-4
num_train_epochs: 3
per_device_train_batch_size: 2
gradient_accumulation_steps: 8
lr_scheduler_type: cosine
warmup_ratio: 0.1
bf16: true
logging_steps: 10
save_steps: 200
output_dir: outputs/lora_emotion_companion
```

**实践建议**：
- 先跑 `rank=8, epoch=1` 的小实验，确认 loss 正常下降、输出不崩坏，再放大；
- 学习率 1e-4 是 LoRA 常见起点，过大易导致风格僵化/复读；
- 保留 base 模型权重，用 `lora_scale` 或提示词开关做 A/B 对比。

## 五、评测方案（微调前后必须同口径对比）

| 维度 | 指标 | 工具 |
| --- | --- | --- |
| 回应质量 | BLEU-4 / ROUGE-L / BERTScore | 成员3 统一自动评测 |
| 抗幻觉 | 幻觉率（人工抽检 + 事实一致性） | 自建 100 条"诱导编造"用例 |
| 共情质量 | 人工 1~5 分评分 | 3 人交叉打分 |
| 安全性 | 高风险话题合规率 | 自建危机话题用例 |
| 性能 | 端到端延迟 | 成员1 性能专项 |

**验收标准（建议）**：BLEU-4 / ROUGE-L / BERTScore 综合分不低于基线，
且幻觉率相对基线下降 ≥ 30%，人工共情评分提升 ≥ 0.5 分。
若微调后综合分反而下降，则应回退到提示词方案。

## 六、风险与成本

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 欠拟合/风格僵化 | 数据量不足或 lr 过大 | 小步实验、早停、保留 base |
| 灾难性遗忘 | 过度微调削弱通用能力 | 低 rank、少 epoch、混入通用指令数据 |
| 与 RAG 冲突 | 微调后模型更"自信"，反而易编造 | 训练数据中必须包含抗幻觉样本 |
| 资源 | 需 GPU，训练+评测耗时 | 先确认成员1 的部署环境是否有训练资源 |
| 可复现性 | 训练随机性 | 固定 seed、记录超参与数据版本 |

> "提示词 + RAG 深耕"路线，并在报告中说明取舍。
