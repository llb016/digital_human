# 实验设计

> 目标：在无法访问线上评分的前提下，建立一套**可复现、与官方口径一致**的本地评测，
> 让每一次改动都能被量化，而不是靠单条样本的观感判断好坏。

## 一、为什么必须先建评测

项目的第一次尝试是"直接看输出"。拿一条样本跑 0.5B，看到回复通顺就认为可用；
换一条又发现人称错乱。这种判断方式有两个致命问题：

1. **单条样本无法区分"模型能力"和"这一条的运气"**
2. **没有基线，无法知道改动是提升还是倒退**——把提示词改得"看起来更好"，
   实际可能让 2354 条里的 300 条变差

所以先做评测，再做优化。顺序不能反。

## 二、评测集构造

### 2.1 从对话级到预测点级

官方验证集 `val_public.jsonl` 是**对话级**的：900 个对话，每个对话有若干
`prediction_points`（标注点），合计 2354 个。

而线上评测喂给模型的是**预测点级**的：一条输入 = 一个 `id` + 截断到该轮为止的 `history`。

两边形态不同，必须先展开。展开规则（`competition/prepare_val.py`）：

- 按 `prediction_points[].target_user_turn_id` 截断 `turns`
- 只保留最后一条是 `user` 发言的样本（否则该轮不是"待回复"的位置）
- `id` 沿用官方格式 `test_{对话序号:06d}_t{turn_id}`，可直接喂官方 `run_inference.py`

产出 2354 条测试输入 + 2354 条标准答案，**数量与官方验证集完全一致**。

### 2.2 一条都没有丢

| 项 | 数量 |
|---|---|
| 验证集对话数 | 900 |
| 展开后预测点 | 2354 |
| 实际参与评测 | 2354 |
| 缺失 id | 0 |

## 三、指标定义

### 3.1 严格按照官方口径处理空值

官方 README 第 101 行写明：

> 画像子项和记忆引用写为空数组。空值作为该项预测失败参与评分，不会获得该项命中分。

所以本地评分对空值一律计为**未命中**，不做任何"跳过"或"不计入分母"的处理。
这一点很关键：如果本地评分把空值当作"未预测所以不算错"，就会高估所有保守策略的分数，
而线上会无情地打回零分。

### 3.2 三个维度分开报，不合成总分

| 维度 | 指标 |
|---|---|
| 情绪 | 准确率、macro-F1（全 16 类）、每类 P/R/F1、混淆对 Top-N |
| 画像 | 三个子项各自的 micro-P / micro-R / micro-F1、整体 macro-F1、完全匹配率 |
| 回复 | 长度均值/中位/与参考答案的比值、分段数、含反问率、字符级 F1 |

**为什么不合成一个总分**：官方未公布公式和权重。自己拍一个加权总分，
会得到一个"看起来很精确但和线上无关"的数字，用来做决策比没有数字更危险。
分维度报，至少能保证每个结论都指向一个确定的、可解释的变化。

### 3.3 字符级 F1 是辅助指标，不是优化目标

字符级 F1（对参考答案的字袋重合度）有个已知缺陷：**它奖励复读用户原话**。

我们实测过：把模板改回"用用户原话开头"能把这个指标从 0.276 提到 0.306，
但回复会变成用户自己句子的复述。所以我们只把它当参考，不做优化目标。

判断回复质量的真正依据是结构对齐（长度、分段、是否有反问）和人工抽检。

## 四、基线设置

三条基线，用来锚定"什么都不做"和"最简单策略"的位置：

| 基线 | 内容 | 作用 |
|---|---|---|
| `empty` | 四字段全空 | 下界。验证评分逻辑：全空必须得 0 |
| `prior` | 情绪恒猜训练集最高频类（`anxiety`），画像全空 | 验证"押注高频类"能不能蒙分 |
| `rules` | 规则层完整实现 | 主方案基线 |

`empty` 得 0 分是评分脚本的正确性检查——如果它拿到非零分，说明指标实现有 bug。

## 五、消融设计

### 5.1 规则层的贡献拆分

规则层同时覆盖情绪和画像。用 `HYBRID_MODE` 环境变量做四组消融，不需要改代码：

| 模式 | 情绪 | 画像 | 用途 |
|---|---|---|---|
| `off` | 模型输出 | 模型输出 | 对照组 |
| `emotion` | 规则 | 模型输出 | 分离情绪贡献 |
| `profile` | 模型输出 | 规则 | 分离画像贡献 |
| `full` | 规则 | 规则 | 主方案 |

### 5.2 回复来源的贡献

`RESPONSE_SOURCE=model` 与 `template` 各跑一次，对比字符级 F1、长度比、分段数。
这一组在 0.5B 上的结论是**模型生成是负收益**（见技术方案第二节）。

### 5.3 规则剪枝的增量

规则从 v1 到 v3 的改动只有一件事：按实测精确率删掉三个低精度标签的规则。
画像 macro-F1 从 0.187 到 0.347。这组对比说明**"删规则"在这类任务上比"加规则"更有效**。

## 六、复现方式

全部离线，不需要 GPU：

```bash
# 1. 展开验证集
python competition/prepare_val.py

# 2. 生成基线预测并打分
for mode in empty prior rules; do
    python competition/baseline_rules.py --mode $mode --out competition/data/base_$mode/submission.jsonl
    python competition/score.py competition/data/base_$mode/submission.jsonl \
        --label "$mode" --report competition/reports/base_$mode.json
done
```

每次评测的完整报表落在 `competition/reports/*.json`，包含每类 P/R/F1 与混淆对，
可以追溯任意一次改动的具体影响。

## 七、一致性保障

项目里有两处必须保持一致、但物理上分开的实现：

1. 提交包里的 `participant/rules_layer.py`（镜像自包含，不能依赖仓库路径）
2. 评测用的 `competition/baseline_rules.py`（离线跑分）

规则改了一边忘一边，就会出现"本地 0.43、线上 0.38"这种查不出来的问题。
所以加了 `competition/check_sync.py`，逐项比对 14 张规则表 + SFT 数据脚本的
枚举与提示词，不一致直接报错退出：

```
$ python competition/check_sync.py
规则层一致（14 项全部匹配）
SFT 提示词与枚举一致（EMOTIONS / PROFILE_LABELS / SYSTEM_PROMPT / conversation_text）
```
