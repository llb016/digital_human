# 运行记录与调优过程

> 本文按时间顺序记录从接入比赛数据到提交包定型的完整过程，
> 包含每一步的判断依据、失败与修正。所有数字均为本地实测。

## 一、阶段总览

| 阶段 | 内容 | 结论 |
|---|---|---|
| R1 | 打通提交链路（冒烟） | 格式全对，输出质量不合格 |

## 二、R1：提交链路冒烟（2026-11-05）

### 2.1 环境

| 项 | 版本 |
|---|---|
| PyTorch | 2.14.1+cpu（本机无 GPU） |
| transformers | 5.18.0 |
| 基线模型 | Qwen2.5-0.5B-Instruct（`model/qwen2.5`，hidden 896 / 24 层） |

### 2.2 单条冒烟

用官方 `run_inference.py` 跑 `test_inference_data.jsonl` 第一条：

| 模型 | 单条耗时（CPU） | 回复字数 | 情绪判定 | 画像标签数 |
|---|---|---|---|---|
| Qwen2.5-0.5B | 6.7 s | 68 | `relaxed`（错） | 0 |
| Qwen2.5-1.5B | 15.6 s | 61 | `anxiety`（对） | 0 |

格式层面完全通过：四字段齐全、id 合规、性能报告正常、解析失败 0。

### 2.3 两个必须记录的问题

**0.5B 出现角色反转**：

> "嗯，**我**觉得自己可能需要调整一些心态……**我**会尽量保持冷静"

它把用户的处境当成了自己的，用第一人称自述。这类错误在评分里直接扣回复分。

**1.5B 人称正确但内容空泛**：

> "面对失败，我们不能总是纠结于过去……不妨先回顾一下自己的不足之处"

用户说的是"怕重蹈覆辙""心一直悬着"，这两句一个字都没回应到。

**共同问题**：两条都只有 1 段、60 来字、没有反问。而参考答案中位 131 字、两段结构。
画像三项全空，按官方口径 = 该维度 0 分。

## 三、R2：本地评测线与规则基线

### 3.1 为什么必须建评测

R1 的结论建立在 3 条样本上，不足以判断任何改动的价值。先把评测建起来。

`competition/prepare_val.py` 把验证集 900 对话展开为 2354 个预测点，
与官方 `test_inference_data.jsonl` 完全同构。`competition/score.py` 按官方口径打分
（空值计未命中），三个维度分开报。

### 3.2 基线结果

| 方案 | 情绪 acc | 情绪 macro-F1 | 画像 macro-F1 |
|---|---|---|---|
| `empty` 全弃权 | 0.000 | 0.000 | 0.000 |
| `prior` 恒猜 anxiety | 0.319 | 0.030 | 0.000 |
| `rules` v1 | 0.432 | 0.331 | 0.187 |
| `rules` v3 | 0.430 | 0.333 | **0.347** |

### 3.3 关键方法：按实测精确率剪枝

v1 的画像 precision 只有 0.07。逐标签统计后发现，问题不在规则写错，而在触发词太普遍：

| 标签 | 预测 | 命中 | 精确率 | 处理 |
|---|---|---|---|---|
| `pets` | 134 | 89 | 0.66 | 保留 |
| `games` | 79 | 49 | 0.62 | 保留 |
| `sports_fitness` | 88 | 50 | 0.57 | 保留 |
| `career_development` | 619 | 85 | 0.14 | 删除 |
| `social` | 752 | 21 | 0.03 | 删除 |
| `programming_technology` | 359 | 1 | 0.00 | 删除 |

删掉这三个标签后，画像 macro-F1 从 0.187 提到 0.347。

## 四、R3：架构定型

### 4.1 决策依据

三条实测，逐条排除"让模型多做一点"的可能：

1. 0.5B 在官方 JSON 约束下输出 `{"answer":"1"}`，直接放弃；换纯聊天 prompt 又人称反转
2. 模型回复字袋 F1 0.272 < 模板 0.306，长度比 0.21，无分段无反问
3. 画像维度模型 0.000（全空），规则 0.347

于是拆成：**模型只写回复，情绪与画像交规则**。

### 4.2 实现

新增 `participant/rules_layer.py`（零依赖），`run_inference.py` 只插入 3 处共 4 行。
两个环境变量控制行为（`HYBRID_MODE`、`RESPONSE_SOURCE`），便于后续消融与切换。

### 4.3 模板的第一版问题

第一版模板拿用户原话开头，三条回复的开头都是用户自己的句子，一眼能看出是抄的。
改成"开场 + 中间层 + 落点 + 反问"组装，且开场和中间层都按情绪极性分开
（第一版不分，出现过"这个变化挺值得记一下"配"你现在的反应不是脆弱"的错位）。

## 六、R5：提交包补齐与模板修正

### 6.1 补齐模型目录

提交包要求 `participant/model/` 存在且包含 `config.json`，否则 `start.sh` 的
transformers 分支会在加载阶段直接失败。已放入 Qwen2.5-0.5B-Instruct（954 MB）。

同时验证了路径解析：`model_path: "./model"` 由 `ROOT / path` 解析
（`ROOT` 为脚本所在目录），**与当前工作目录无关**。实测从 `C:\Users\林` 启动，
模型仍能正确定位——这一点很关键，因为主办方从 `/root` 执行 `bash /root/participant/start.sh`。

### 6.2 生成参数调整

`max_new_tokens` 从 1200 改为 256。

理由：当前架构下回复由规则层产出，模型输出不参与最终结果；256 足够覆盖
"切回模型生成"时的正常回复（参考答案中位 131 字 ≈ 81 token），
同时把单条耗时降到原来的约 1/5。

### 6.3 发现并修复一个选择器 bug

模板选句用 `_pick(options, seed)` 按 `crc32(seed) % len(options)` 稳定选择。
看起来没问题，实测发现：

**`crc32(id+"o")` 与 `crc32(id+"m")` 取模后完全同余**——2000 个 id 的联合分布
只有 4 种组合，而不是 16 种。原因是 crc32 是线性函数，后缀 `"o"`(0x6F) 与
`"m"`(0x6D) 只差 2，取模 4 后低两位相同。

后果：开场和中间层永远配套出现，**扩池子完全无效**。2354 条里有 150 条首段一字不差。

改用 md5 取前 4 字节（有雪崩效应）后：

| 版本 | 唯一首段 | 最高频首段 | 唯一完整回复 | 最高频完整回复 |
|---|---|---|---|---|
| v5 最初 | 18 | 165 次 | 282 | 47 次 |
| v7 中间态 | 24 | 150 次 | 447 | 46 次 |
| **v8 换 md5 后** | **36** | **114 次** | **508** | **28 次** |

重复率下降约 40%，各项指标完全不变（情绪 0.430、画像 0.347、回复 111 字）。

### 6.4 正向分支的逻辑错误

实测输出里出现过：

> "能走到这一步，是你自己一点点撑出来的，不是运气。……这种踏实感值得被记住……
> **你现在最想先处理哪一块？**"

前半句在肯定，后半句却在问"还有什么问题要处理"。原因是正向和负向共用同一套反问，
而那三个反问都预设"还有待处理的困难"。

修正：新增 `QUESTIONS_POSITIVE`（3 个），并把正向落点按具体情绪细分
（`relaxed` / `gratitude` / `pride` / `joy` / `neutral` / `care` / `surprise` 各一句）。

## 七、提交包最终验证

用官方样例数据 `test_inference_data.jsonl`（3 条）完整跑通：

| 指标 | 多次运行范围 |
|---|---|
| 解析失败数 | 0（三次运行均为 0） |
| 中位耗时 | 3.97 ～ 7.89 s |
| 平均耗时 | 5.69 ～ 8.28 s |
| p95 耗时 | 11.68 ～ 12.71 s |

耗时全部来自 CPU 推理（本机无 GPU），波动较大：同一份 3 条数据在三次运行中，
中位耗时从 3.97 s 变到 7.89 s。原因是本机同时有其他进程占用 CPU，
单条耗时里 prefill 与 decode 的比例会随负载变化。

另一个影响因素是历史长度：`test1_000001_t7`（第 2 条）历史最长，
其耗时是另两条的 2～3 倍。

赛道镜像有 GPU，transformers 后端的推理速度会显著高于本机 CPU 数据；
本表仅用于验证"能跑通、解析零失败"，不作为性能预期。

产物 `submission.jsonl` 与 `performance_report.json` 均通过官方校验，存放在
`运行记录/` 目录下。

## 八、遗留问题

1. **回复多样性仍然有限**：114 条共用同一首段（占 4.8%）。纯模板方案的固有上限，
   要真正解决需要理解上下文生成，即微调。
2. **情绪 0.430 是规则上限**：剩余误差集中在 `relaxed` 与 `anxiety` 的互相误判，
   需要理解对话阶段才能分开。
3. **未做微调**：数据与训练脚本已就绪，受算力限制未执行。
