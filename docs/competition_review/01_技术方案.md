# 技术方案：数字人综合情感陪伴对话模型

> 参赛作品说明 · 2026 年 11 月

## 一、任务理解

平台的输入输出是固定的：

**输入**：一段多轮对话 `history`（user / assistant 交替），截止到最新一条用户消息。

**输出**：一个 JSON object，四个字段：

| 字段 | 含义 | 取值约束 |
|---|---|---|
| `response_text` | 下一轮助手回复 | 非空中文 |
| `emotion_label` | 最新用户消息的情绪 | 16 类英文标签 |
| `user_profile` | 用户画像，三组数组 | personality 10 类 / interests 12 类 / style 11 类 |
| `memory_refs` | 记忆引用 | 测试集无 memory bank，恒为 `[]` |

情绪标签共 16 类：`anger` `anxiety` `care` `disgust` `fear` `gratitude` `helplessness`
`joy` `loneliness` `mixed` `neutral` `pride` `relaxed` `sadness` `shame` `surprise`。

这套标签**不是任何通用情感分类体系**。`relaxed`、`helplessness`、`loneliness`、`mixed`
是本次任务自有的类，对应中文语境里"松了口气""没辙了""心里空落落的""又气又觉得自己傻"
这类状态。这一点在后面反复出现，是很多实现踩坑的地方。

评分按 README 第 101 行的口径：**空字符串和空数组一律计为该项未命中**，不给部分分。
所以"没把握就输出空"这个策略在画像维度上是纯亏——不猜就是零分。

## 二、系统架构

我们的方案是**生成与分类分离**：

```
输入 history
   │
   ├─→ Qwen2.5-0.5B-Instruct ──→ response_text（自然语言回复）
   │
   └─→ 规则层 rules_layer.py ──→ emotion_label
                              └─→ user_profile（三组标签）
                                        │
                                        ▼
                              postprocess() 合并 → submission.jsonl
```

模型负责它擅长的事（说人话），规则负责它擅长的事（按标注分布做分类）。

### 为什么这么分

这不是设计偏好，是三个实测结论逼出来的。

**1. 让 0.5B 同时输出四类信息的 JSON，它会直接崩**

同一条样本（用户说导师要求大改论文、只剩两周），两种提示词的结果：

| 提示词 | 模型输出 |
|---|---|
| 官方 JSON 约束 | `{"answer":"1"}` —— 直接放弃作答 |
| 纯聊天、不要 JSON | "导师，我理解你的压力很大……希望你能保持冷静" —— 人称错乱，把用户当成了导师 |

同一个模型，加了 JSON 约束就放弃，去了 JSON 约束就角色反转。这不是提示词能修好的问题，
是模型体量不够。

**2. 它的回复质量还不如模板**

3 条验证集样本上的对比：

| 指标 | 0.5B 生成 | 规则模板 |
|---|---|---|
| 字符级 F1 | 0.272 | 0.306 |
| 长度比（对参考答案） | 0.21 | 0.61 |
| 分段 | 1 段 | 2 段 |
| 含反问 | 否 | 是 |

参考答案的中位长度是 131 字、普遍两段结构（先共情复述，再给方向或反问）。
0.5B 输出 60 来字、一段、没有反问。在这个体量下，让它生成是**负收益**。

**3. 分类任务上，规则全面胜出**

| 维度 | 0.5B 零样本 | 规则层 |
|---|---|---|
| `user_profile` macro-F1 | **0.000**（三项全空，按口径不得分） | **0.347** |
| `emotion_label` 准确率 | 约 0.30（接近恒猜高频类的 0.319） | **0.430** |

模型在画像维度上输出全空，等于弃权得零分；规则给出 0.347。

## 三、规则层怎么做的

规则层（`participant/rules_layer.py`，零第三方依赖，可直接进镜像）做三件事。

### 3.1 情绪判定：先验 + 词面加权，按精度剪枝

```
score[label] = prior[label] + Σ (规则命中次数 × 权重)
```

先验来自训练集分布（`anxiety` 34.0%、`relaxed` 15.1%、`helplessness` 8.4% …），
权重来自对验证集真实语料的区分度统计（按类统计二字片段相对全库的 lift）。

关键的一步不是加规则，是**删规则**。第一版写了十几类关键词，画像 precision 只有 0.07；
逐标签统计后发现原因是触发词在语料里太普遍：

| 标签 | 预测次数 | 命中 | 精确率 | 处理 |
|---|---|---|---|---|
| `pets` | 134 | 89 | 0.66 | 保留 |
| `games` | 79 | 49 | 0.62 | 保留 |
| `sports_fitness` | 88 | 50 | 0.57 | 保留 |
| `career_development` | 619 | 85 | 0.14 | **删除** |
| `social` | 752 | 21 | 0.03 | **删除** |
| `programming_technology` | 359 | 1 | 0.00 | **删除** |

"工作""面试""朋友"这些词几乎每篇对话都有，但标注里极少给对应标签。
这些关键词不是弱信号，是**负信号**——它们把 precision 拉下来，还挤掉了真信号的位置。

人格维度更极端：10 类里只有 `sensitive` 有信号（P=0.26，金标覆盖 20.7%），
其余 9 类精确率全部≈0。所以最终只输出 `["sensitive"]`。与其贴一堆错的，不如只贴一个对的。

这一刀下去，画像 macro-F1 从 **0.187 提升到 0.347（+86%）**。

### 3.2 兜底回复：按情绪组装，不复述用户原话

当模型输出不可用时（长度 < 20 字、或检测到复读），用模板兜底。

模板结构对齐参考答案：`开场 + 中间层 + 落点 + 反问`，两段。

- **开场**按情绪极性与 `sample_id` 稳定选取，同一输入永远同一句（可复现），
  不同样本之间能拉开。选取用 `md5(seed)` 而非 `crc32`：crc32 是线性函数，
  加不同后缀取模后会同余，导致开场与中间层永远配套出现（详见运行记录 6.3）
- **中间层**分正向 / 负向两套。第一版没分，出现过"这个变化挺值得记一下"配
  "你现在的反应不是脆弱"的错位
- **落点**按具体情绪分支：`anxiety` 给拆解、`helplessness` 给"先只做一件"、
  `sadness` 给允许难过、`mixed` 给"两种感受可以同时成立"；正向侧 `relaxed` /
  `gratitude` / `pride` / `joy` / `neutral` / `care` / `surprise` 各有一句
- **反问**也分正向 / 负向两套。负向的三个都预设"还有待处理的困难"，
  配在"这种踏实感值得被记住"后面会自相矛盾（实测出现过）

这里有一个主动的取舍：第一版模板拿用户原话开头，字符级 F1 是 0.306，比现在高 0.03。
但那是靠**复读用户原话**换来的，三条回复的开头都是用户自己的句子，一眼能看出。
字符级 F1 这个指标本身奖励复读，我们没为这 0.03 改回去。

### 3.3 合并与开关

`postprocess()` 把规则结论与模型输出合并，并置 `memory_refs = []`。

两个环境变量控制行为，不需要改代码：

| 变量 | 取值 | 说明 |
|---|---|---|
| `HYBRID_MODE` | `off` / `emotion` / `profile` / `full` | 覆盖哪些字段，`full` 为默认 |
| `RESPONSE_SOURCE` | `template` / `model` / `auto` | 回复来源。默认 `template`；`auto` 会检测复读并退回模板 |

留这两个开关，是为了让**消融实验不用改代码**，也为将来换更强的模型留出口：
如果以后有了微调过的 7B，把 `RESPONSE_SOURCE=model` 即可切回生成，架构不用动。

## 四、为什么没有做微调

诚实说明：**本次没有做 SFT，原因是算力**。

训练集有 8338 个对话、18657 个带完整标注的预测点，数据质量足够做监督微调。
我们完成了全部数据工程，并在本地验证通过：

- 展开为 17286 条训练样本（train 17065 / dev 221，按 `conversation_id` 切分防泄漏）
- 训练目标经官方 `parse_prediction()` 复验 400 条：解析失败 0、标签改写 0、画像改写 0
- 分词与 mask 对齐在 500 条上验证通过（`max_length=4096`，零丢弃）
- 用官方分词器实测 token 预算：0.62 token/字符，p99=3712，4096 足够覆盖 99.7%

但本地只有 CPU，7B 模型无法训练；赛道镜像虽有 GPU，训练与提交的时间窗口也不允许。
用 0.5B / 1.5B 做微调同样不划算——1.5B 在本次任务上已经表现出"通顺但空泛"，
继续压小模型不如把规则做扎实。

数据管线与训练脚本都保留在项目仓库中（`competition/prepare_sft.py`、
`competition/train_lora.py`），换到有 GPU 的环境可直接执行。

## 五、提交包结构

```
/root/participant/
├── run_inference.py           官方脚本 + 3 处插入共 4 行
├── rules_layer.py             规则层（本次新增，零依赖）
├── start.sh                   官方启动脚本，未修改
├── configs/inference_config.json
├── model/                     Qwen2.5-0.5B-Instruct（954 MB）
├── requirements.txt
└── templates/
```

对官方脚本的改动仅 4 行，不改变任何产物结构、不绕过 schema 校验：

```python
import rules_layer                                              # ① 导入

prediction, parse_failed = parse_prediction(sample["id"], decoded)
prediction = rules_layer.postprocess(sample, prediction)         # ② 解析后合并

print(f"规则后处理模式: {rules_layer.current_mode()} | ...")     # ③ 启动打日志
```

配置改动两处：

| 项 | 原值 | 改后 | 原因 |
|---|---|---|---|
| `generation.max_new_tokens` | 1200 | 256 | 当前架构下回复由规则层产出，模型输出不参与最终结果；256 足够覆盖"切回模型生成"时的正常回复（参考答案中位 131 字≈81 token），同时把单条耗时降到原来的约 1/5 |
| `hardware_label` | `fill-in-before-official-run` | `competition-runtime` | 占位符不应出现在性能报告中 |

## 六、已知限制

1. **回复由模板产出，多样性有限。** 同一情绪极性下只有 3 种开场 × 4 种中间层 × 3 个反问，
   在 2354 条规模上会出现重复句式。这是无模型生成方案的固有代价。
2. **情绪准确率 0.430 已接近"不用模型"的上限。** 剩余误差集中在 `relaxed` 与 `anxiety`
   的互相误判（对话收尾处的"松了口气"与真正的焦虑在词面上高度重叠），需要理解对话阶段
   才能分开，规则做不到。
3. **画像只输出 `sensitive` 与少数兴趣标签**，覆盖面窄但精度可控。这是精度优先的取舍，
   如果官方评分对召回更敏感，这个策略会吃亏。
4. **未做微调**，见第四节。
